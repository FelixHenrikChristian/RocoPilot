# 运行日志

## 日志在哪里看

| 去向 | 内容 | 保留 |
| --- | --- | --- |
| 日志页（导航栏底部） | 本次运行的记录。级别开关按调试、信息、警告、错误从低到高排列；调试默认关闭，打开后和其余记录按时间混排 | 信息及以上最近 5000 条，调试记录另算最近 5000 条 |
| `app-日期.log` | 信息、警告、错误，和日志页默认显示的是同一批记录 | 按天滚动，保留 14 个文件 |
| `debug-日期.log` | 上面的全部，加上调试记录，以及出现警告或错误时回放的逐次识别记录 | 按天滚动，单个文件 20 MB，最多 10 个文件、7 天 |

两个文件都在「设置 → 文件目录 → 日志目录」。反馈问题时，`app` 文件说明发生了什么，`debug` 文件用来查原因。

日志页的「调试」指日志的 Debug 级别，和信息、警告、错误是同一套级别里最低的一档，内容与 `debug` 文件里的 `[DBG]` 行相同。Visual Studio 的输出窗口只是另一个去向，调试运行时所有级别的记录都会在那里出现一份。

热键辅助进程是单独的进程，只在异常退出时往 `app` 文件写一条。

## 级别

| 级别 | 写给谁 | 何时使用 | 示例 |
| --- | --- | --- | --- |
| Information | 用户 | 已经发生的操作和结果，用户读得懂、关心的事 | 进入战斗、遇到精灵、每回合做了什么、血脉、发起捕捉、奇遇 +1、任务开始和结束 |
| Warning | 用户 | 出了意外，但程序自己兜住了，功能还在继续 | 读设置失败改用默认值、截图失败后重试、通知没发出去、GitHub 请求失败改用备用源 |
| Error | 用户 | 用户要做的事没做成，需要用户知道或处理 | 实时任务启动失败（找不到窗口、获取不到画面、分辨率不支持）、任务异常终止、设置保存失败、换精灵 6 个位置都失败 |
| Fatal | 用户 | 应用即将崩溃退出 | 未处理异常 |
| Debug | 开发者 | 排查问题需要的技术细节 | 识别结果的变化和汇总、实际发送的按键、点击坐标、分辨率映射、场景变化 |
| Trace | 开发者 | 逐次识别结果，量很大 | 每一次图像匹配的分数、每一次 OCR 的原文 |

判断 Warning 还是 Error，只问一句：**这件事最后做成了吗？** 换了条路做成了、或者下一轮会自动重试，是 Warning；没做成、要用户介入，是 Error。同一个操作由触发方式决定级别时按这条判断，例如手动检查更新失败是 Error，启动时自动检查失败是 Warning。

## 写法

- 消息用中文，使用命名占位符，不拼接字符串；异常作为第一个参数传入，不写进消息。
- Information、Warning、Error 是给用户看的：以功能名开头（`自动战斗：`、`实时任务：`、`奇遇统计：`、`云同步：`），说清发生了什么和影响；不带 `Key=Value` 字段、内部类名和方法名，不加句末句号。
- 技术细节单独记一条 Debug 跟在后面。例如「自动战斗：第 3 回合，发起捕捉（奇异血脉）：栗鼠」是 Information，「第 3 回合已发送按键 W, 1, Space」是 Debug。
- Warning 写明程序接下来怎么处理（已使用默认值、稍后重试、改用备用源）。Error 写明没做成的是什么。
- 一件事只记一次，在知道结果的那一层记。下层只是把失败原样返回或抛出时不记，或者只记 Debug；避免同一个失败在两层各出现一条 Warning。
- 只有发了按键才能说「发起捕捉」，程序并不知道捕捉有没有成功，不写「捕捉成功」。同理，日志只写程序确实知道的事。
- 不为了写日志额外做识别或查询。

## 高频内容怎么记

实时识别每秒二十多次（场景和按钮的模板匹配、异色、血脉、精灵名），逐次写日志一小时约八万行。按下面的方式控量，三种机制各管一件事。

**识别结果：只在一处上报。** 图像匹配服务和文字识别服务在返回结果时各调用一次 `RecognitionDiagnostics`，其余代码不再为识别结果写日志，也不传任务名、不自己算指纹。它负责三件事：

1. 每一次结果记一条 Trace；
2. 同一个目标的结果变了（命中变未命中、命中数量变化、OCR 文字变化）记一条 Debug，带分数和阈值。结果在阈值附近抖动时，先连记 4 条，之后每 5 秒放行一条，并注明中间跳过了几次；
3. 每 30 秒为每个被用到的目标记一条汇总：次数、命中次数、变化次数、分数范围、耗时。任务暂停或结束时把最后一段汇总写出。

**逐次记录：出问题时回放。** Trace 平时不写文件，只在内存里保留最近 300 条。出现 Warning 或 Error 时，`FrameTraceSink` 把这 300 条连同前后标记补写进 `debug` 文件，再写触发它的那一条；两次回放至少间隔 30 秒。没有“打开后全量记录”的开关：全量日志平时没人会开，偶发问题出现之后再开又复现不了，现场只能靠这段回放留住。没有触发 Warning 或 Error 的问题（比如识别错了但程序照常执行）不会回放，查这类问题看变化记录和 30 秒汇总。

**循环里重复的故障：只记第一次和之后每 30 秒一次。** 截图失败、识别出错、按键没发出去这类故障会在每一轮循环里重复。用 `RepeatedFailureGate` 包住，后续的记录里注明跳过了几次；故障消失后可据返回值记一条「已恢复」。

日常任务（种菜、出售、邮件、通行证、晚风小憩、体力合成）每一轮都上报进度，调度服务只在进度内容变化时记一条 Information，任务本身不写日志。

## 各功能的记录

| 功能 | Information | 另有 Debug |
| --- | --- | --- |
| 应用、更新 | 启动版本与运行环境、检查更新的结果、正常关闭 | 更新源切换 |
| 实时任务 | 启动（窗口、分辨率、自动战斗和奇遇统计是否开启）、挂起、恢复、停止、截图恢复 | 截图、OCR、匹配、输入方式和配置路径；场景变化 |
| 战斗 | 进入战斗、遇到精灵、血脉识别、奇遇效果解除、每回合的动作、发起捕捉及目标、换精灵结果、技能失败的游戏提示、发现异色、战斗结束（回合数和用时） | 实际发送的按键、血脉和异色提示原文、奇遇解除判定的分数 |
| 奇遇统计 | 计数 +1、暂存、账号确认状态 | UID 识别过程 |
| 独立任务、每日清单 | 当前子任务和清单序号、每一步进度、挑战成功次数、扫描结果、结束、取消、每日汇总 | 键鼠操作、点击坐标和模板分数 |
| 云同步、图鉴 | 下载合并或上传完成、图鉴同步数量 | 文件大小 |
| 设置、热键、遮罩 | 开关变化、热键监听启动、截图保存路径、配置导入导出 | 窗口显示状态、辅助进程 PID |

## 改日志时的检查

- 占位符数量和实参数量一致。
- 新增的循环内日志有没有控量。
- 新增的 Warning 或 Error 会不会和调用方重复。
- `RocoPilot.Tests` 里的 `LoggingHelperTests`、`FrameTraceSinkTests`、`RecognitionDiagnosticsTests`、`LogEntryStoreTests`、`LogViewModelTests` 覆盖日志管线和控量逻辑，改这几处后要跑。
